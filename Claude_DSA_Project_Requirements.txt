# Project Requirements for Claude — Smart Emergency Blood Allocation & Dispatch Engine

## 1. Your Role and Goal

Act as a senior full-stack engineer and a Data Structures and Algorithms (DSA) teaching mentor. Design and implement a **small-to-medium, fully functional academic course project** for a second-year B.Tech Fundamentals of Data Structures subject.

The project must be realistic enough to demonstrate a useful workflow, but **must not become a major hospital-management system**. Its main purpose is to demonstrate correct, visible, and testable implementation of the data structures and algorithms in the syllabus.

Build a working web application named:

**Smart Emergency Blood Allocation & Dispatch Engine**

Tagline: **Prioritize urgent requests. Allocate compatible stock. Reduce expiry waste.**

Use the attached synopsis as the project’s starting point. It describes emergency blood requests, urgency-based prioritization, blood inventory, First-Expired-First-Out (FEFO) allocation, compatibility checks, sorting/searching, and dispatch logs.

---

## 2. Problem Statement

Blood banks may need to manage multiple hospital requests with different urgency levels while tracking blood bags with different blood groups, quantities, collection dates, and expiry dates. Handling these records manually can make it harder to prioritize critical requests, find compatible available stock, and dispatch stock that is closer to expiry.

This project simulates a blood-bank inventory and dispatch workflow. It stores blood stock and hospital requests, prioritizes requests according to urgency and arrival time, checks a configurable blood-compatibility rule set, allocates eligible stock using FEFO, and records the result of each allocation attempt. A dashboard displays stock levels, pending requests, expiry warnings, and dispatch history.

**Important scope boundary:** This is an educational simulation, not a clinical decision-support system. Do not present the allocation result as medical advice or as suitable for real-world transfusion decisions. Compatibility rules must be clearly labelled as simplified educational rules and should be verified by qualified professionals before any real-world use. Do not connect to real hospitals or handle real patient-identifying data.

## 5. Functional Requirements

### 5.1 Dashboard
Show:
- Total available, non-expired units
- Total registered blood bags
- Pending requests
- Critical requests waiting
- Bags expiring soon (for example, within 7 days; make this threshold configurable)
- Recently completed dispatches
- Blood-group stock summary

Dashboard counts must come from actual database/application state, not hard-coded values.

### 5.2 Blood Inventory
The user must be able to:
- Add a blood bag/unit record
- View all stock with search, filters, and sorting
- View stock by blood group and availability status
- Update editable details
- Mark stock as unavailable/removed through a controlled action
- See expired stock clearly separated from usable stock

Suggested fields:
- `id` / `bagId`
- `bloodGroup` (A+, A-, B+, B-, AB+, AB-, O+, O-)
- `collectionDate`
- `expiryDate`
- `volumeMl` (optional; if included, keep it consistent)
- `bloodBankName` or `location` (keep this simple)
- `status` (available, reserved, dispatched, expired, discarded)
- `createdAt`

Validation:
- Blood group must be one of the supported values.
- Expiry date must be later than collection date.
- A dispatched, discarded, or expired bag cannot be allocated again.
- Do not allow duplicate bag IDs.
- Use synthetic data only.

### 5.3 Hospital Requests
The user must be able to:
- Create a request
- View pending, partially fulfilled, fulfilled, and cancelled requests
- View request priority and arrival order
- Process the next highest-priority request
- See which bags were allocated and why
- See an explicit shortage message if not enough compatible stock exists

Suggested fields:
- `id` / `requestId`
- `hospitalName`
- `requiredBloodGroup`
- `unitsNeeded`
- `urgencyLevel` (1 = Critical/Trauma, 2 = Surgery, 3 = Routine)
- `createdAt` / arrival sequence
- `status` (pending, partially_fulfilled, fulfilled, cancelled)
- `unitsAllocated`
- `notes` (optional; no patient-identifying information)

Validation:
- Units needed must be a positive integer.
- Urgency must be 1, 2, or 3.
- A request that has been fulfilled or cancelled cannot be processed again.
- Request timestamps and arrival sequence must be stable enough to break priority ties.

### 5.4 Request Processing and Allocation
When the user chooses **Process Next Request**:
1. Select the highest-priority pending request using a custom binary heap.
2. Break ties by earlier arrival time/sequence.
3. Remove expired stock from eligibility before allocation; expired stock must never be allocated.
4. Determine eligible donor blood groups using a clearly documented, simplified compatibility lookup table.
5. Among eligible stock, allocate the bags with the earliest expiry date first (FEFO).
6. Allocate only the number of units actually available and compatible.
7. Update inventory and request status consistently.
8. Record a dispatch/allocation log containing the request, allocated bag IDs, date/time, and outcome.
9. If stock is insufficient, mark the request partially fulfilled or still pending according to a clearly documented policy. Recommended simple policy: record the fulfilled units, set `partially_fulfilled` if at least one unit was allocated, and leave the unfulfilled quantity visible. If none could be allocated, leave it pending and report the shortage.
10. Display a readable explanation: selected request, priority reason, compatibility groups considered, bags chosen by FEFO, and any remaining shortage.

Do not silently lose or skip requests. Define and test what happens to a partially fulfilled request in the priority queue. A practical simple policy is to reinsert a partially fulfilled request with its remaining units and original arrival sequence, while avoiding an infinite automatic processing loop. The UI should process only one request per click.

### 5.5 Search, Sort, and Filters
Provide:
- Search inventory by bag ID
- Filter inventory by blood group and status
- Sort inventory by expiry date, collection date, or blood group
- Search requests by request ID or hospital name
- Filter requests by status and urgency
- Sort dispatch history by time

Use the custom algorithms described in Section 7 for the relevant operations. It is fine to use database indexes for persistence, but the DSA demo operations must explicitly run the project’s own implementations.

### 5.6 Dispatch History
Show:
- Request ID and hospital
- Requested blood group and quantity
- Allocated bag IDs and actual donor groups
- Time of processing
- Number fulfilled and remaining
- Result (fulfilled, partially fulfilled, no stock)
- A short explanation of the allocation decision

Dispatch history should be append-only from the user’s perspective. Do not allow users to edit old dispatch records casually.

### 5.7 DSA Demonstration Page
Include a simple page or panel called **DSA Lab** that demonstrates the actual data structures used:
- Add sample requests and show the binary heap’s root / processing order
- Show a per-blood-group FEFO structure ordered by expiry
- Run linear search and binary search on suitable sample arrays
- Run Merge Sort and Quick Sort on a sample inventory list and show before/after order
- Show BFS/DFS only if a graph feature is actually included; do not add a fake or disconnected graph demo just to claim coverage
- Show a small hash-table lookup for bag ID or blood-group lookup if implemented
- Display operation counts or simple time-complexity notes, not misleading benchmark claims

The main application must still use the same DSA implementation as the DSA Lab. Do not create a separate fake demo implementation.

## 6. DSA Analysis Against the Course Syllabus

The course syllabus covers arrays/searching/sorting, linked lists, stacks/queues, trees, graphs, and hashing. The project should implement a **focused subset well**, rather than forcing every syllabus topic into one app.

### A. Highest priority — directly useful to the problem

#### 1. Binary Heap / Priority Queue — MUST IMPLEMENT
**Use:** Select the next emergency request.

- Implement a custom binary heap (prefer a min-heap by priority key, or a max-heap with a clearly defined comparator).
- Priority order: urgency level 1 before 2 before 3; within the same urgency, earlier arrival sequence first.
- This ordering is clearer and safer for an academic implementation than the synopsis’s ambiguous composite score formula.
- Do not rely on a built-in priority queue library.
- Operations: insert, peek, extract/remove root, heapify/rebuild if needed.
- Expected complexity: peek `O(1)`, insert `O(log n)`, extract `O(log n)`, build heap `O(n)`.

**Correctness requirement:** If using a comparator, centralize it and unit-test it. Do not mix “level 1 is most urgent” with numeric max-heap logic without explicitly handling the direction.

#### 2. FEFO Inventory Structure — MUST IMPLEMENT
**Use:** Choose the available compatible bag with the earliest expiry date.

Recommended implementation: maintain a separate custom **min-heap per blood group**, keyed by expiry date and then bag ID. This directly demonstrates heap operations and makes the next-to-expire eligible bag available at the root.

- Insert bag: `O(log n)`
- Peek earliest expiry: `O(1)`
- Remove earliest expiry: `O(log n)`
- Remove expired stock from the eligible structure or skip it safely and mark its status as expired.
- Keep the database as the persistent source of truth and synchronize inventory status and heap contents after every operation.
- Avoid claiming that a whole heap can be “swept” in `O(1)`: only checking the root is `O(1)`; removing each expired root costs `O(log n)` per removal.

#### 3. Blood-Group Compatibility Lookup — MUST IMPLEMENT
**Use:** Decide which stock groups can be considered for a requested group.

- Use a fixed, clearly documented lookup table / compatibility matrix for the **educational simulation**.
- Keep compatibility logic in a dedicated, unit-tested function/module.
- Do not infer compatibility from string comparisons.
- The matrix must be applied consistently before any bag is allocated.
- Make the interface show the requested group and eligible stock groups.
- Important: real transfusion compatibility is more nuanced than a simple ABO/Rh table and depends on clinical testing and protocols. Clearly label this as simplified educational logic and never describe it as safe for real transfusions.

#### 4. Sorting — MUST IMPLEMENT AT LEAST TWO
**Use:** Sort stock by expiry date, collection date, or group for inventory views and analytics.

Recommended:
- **Merge Sort:** stable, `O(n log n)` time, typically `O(n)` auxiliary space.
- **Quick Sort:** average `O(n log n)`, worst case `O(n²)`; use a randomized or median-of-three pivot if appropriate, or clearly document the pivot choice.

Implement these yourself for arrays of inventory records. The UI must allow a user to trigger the sort and see the sorted result. Use a deterministic tie-breaker such as bag ID.

Do not claim that Quick Sort is always `O(n log n)`; document its worst case.

#### 5. Searching — MUST IMPLEMENT AT LEAST TWO, WITH CORRECT PRECONDITIONS
- **Linear Search:** use for unsorted records, such as finding a bag ID in a current list. Complexity `O(n)`.
- **Binary Search:** use only on an array sorted by the exact search key. For example, sort bag records by bag ID and then binary-search by bag ID. Complexity `O(log n)` after sorting; sorting cost must not be hidden when reporting end-to-end cost.

**Important correction to the synopsis:** Binary search should not be applied directly to a heap’s internal array because a heap is not globally sorted. Use binary search on a sorted array, or use a hash lookup for exact IDs.

Optional: Fibonacci Search may be included in the DSA Lab only if implemented correctly on a sorted array. It is not required for the core workflow.

#### 6. Hash Table — RECOMMENDED, SMALL ADDITION
**Use:** Fast lookup by unique bag ID or request ID.

- Implement a custom hash table with separate chaining or open addressing.
- Explain hash function, collision handling, and average/worst-case lookup complexity.
- Use it for exact ID lookup if the implementation remains manageable.
- If the database is used for ordinary app reads, make it clear that the custom hash table is an in-memory DSA structure used by the project’s search/index layer, not a replacement for persistent storage.

### B. Useful but optional

#### 7. Queue / Circular Queue
A queue can represent arrival order or a small dispatch-processing buffer. However, the emergency request priority queue must be the heap, not a plain FIFO queue, because urgency changes the processing order.

If implementing a circular queue, use it for a clearly defined bounded event/log buffer or a separate arrival-order view. Do not add it merely to claim syllabus coverage.

#### 8. Linked List
A singly linked list can represent a simple append-only in-memory dispatch event list, or a small demonstration of insertion/deletion/traversal. But a linked list is not automatically the best structure for inventory searching or FEFO allocation. If time is limited, do not prioritize it over heap, compatibility, search, and sorting.

#### 9. Arrays
Arrays are naturally suitable for inventory snapshots, sorted lists, binary search, Merge Sort, and Quick Sort. Use them explicitly in the algorithm modules.

### C. Do not force these into the project
The following syllabus concepts are not needed for the core problem and should be omitted unless there is a genuinely useful extension:
- Sparse matrix transpose
- Generalized linked lists
- Stack-based infix/prefix/postfix conversion and evaluation
- Josephus problem
- Binary search trees / threaded binary trees
- BFS/DFS, bipartite graph, cycle detection, Prim’s/Kruskal’s MST, shortest paths, Union-Find
- Extendible hashing
- Radix Sort, Shell Sort, Bucket Sort, Heap Sort as separate sorting algorithms beyond the heap data structure already required

Do not add an unrelated graph/network visualizer simply to tick more syllabus topics. The project will be stronger if it demonstrates a smaller set correctly and explains why those structures fit the problem.

## 7. Suggested DSA Module Design

Keep DSA logic separate from Express routes and React components. Use TypeScript types and small modules such as:

```text
server/
  src/
    dsa/
      BinaryHeap.ts
      FefoInventory.ts
      mergeSort.ts
      quickSort.ts
      linearSearch.ts
      binarySearch.ts
      HashTable.ts              # recommended, if time permits
    domain/
      compatibility.ts
      allocationService.ts
      priority.ts
    routes/
      inventory.routes.ts
      requests.routes.ts
      dispatch.routes.ts
      analytics.routes.ts
    db/
      schema.sql
      database.ts
    tests/
      BinaryHeap.test.ts
      FefoInventory.test.ts
      sorting.test.ts
      searching.test.ts
      compatibility.test.ts
      allocationService.test.ts
```

Names can vary, but keep this separation:
- `dsa/`: generic data structure and algorithm implementations
- `domain/`: application rules and orchestration
- `routes/`: HTTP request/response handling
- `db/`: persistence
- `tests/`: automated correctness tests

Do not put heap implementation directly inside a route handler or React component.

### Priority comparator
Use a single comparator for request priority. Recommended order:
1. Smaller urgency number first (1, then 2, then 3)
2. Earlier arrival sequence first
3. Request ID as deterministic final tie-breaker

This avoids ambiguity around composite scores and makes the behavior easy to explain during assessment.

### FEFO ordering
For eligible stock in each donor blood group:
1. Earliest expiry date first
2. Bag ID ascending for equal expiry dates

Before allocation, exclude expired bags and bags not in `available` status. When a bag is allocated, persist the status change and remove it from the available FEFO structure.

### Allocation transaction safety
An allocation must not leave the database and in-memory structures inconsistent:
- Validate the request and stock first.
- Determine the planned bag IDs.
- Persist allocation/status updates together in a database transaction where supported.
- Update/rebuild the relevant in-memory structures after the transaction succeeds.
- If the transaction fails, do not report a successful dispatch.
- On server startup, rebuild heaps/indexes from current database records rather than assuming in-memory state survived a restart.

## 8. Blood Compatibility Rules: Treat as a Configurable Educational Table

Implement a module such as `getCompatibleDonorGroups(requiredGroup)` that returns a list of donor groups considered eligible by the simulation.

The project synopsis refers to an 8×8 compatibility matrix and gives examples such as O− as a broad donor group and AB+ as a broad recipient group. Use a well-documented **red-blood-cell compatibility teaching table** only as a simplified demo assumption, and ensure the table direction is explicit:

- Input = recipient/requested blood group
- Output = donor stock groups the simulation permits for that recipient

Do not reverse donor-to-recipient and recipient-from-donor directions. Add tests for all eight requested groups and include tests for broad examples such as O− donor stock being considered for multiple recipients and AB+ recipient being able to receive from multiple donor groups under the simplified table. Explain that this is not a clinical validation system.

## 12. Required Correctness and Test Cases

At minimum, write automated tests for the following.

### Heap / priority queue
- A critical request is processed before a routine request even if the routine request arrived first.
- Two requests with equal urgency are ordered by arrival sequence.
- Empty heap behavior is defined.
- Insert, peek, extract, and heap ordering are correct after multiple operations.

### FEFO
- Earliest-expiring eligible bag is allocated first.
- Equal expiry dates use the defined deterministic tie-breaker.
- Expired bags are never allocated.
- Dispatched/unavailable bags are never allocated again.
- A newly added bag appears in the correct group structure.
- After server restart, in-memory structures rebuild from persisted data.

### Compatibility
- All eight requested groups have a defined result.
- The matrix direction is recipient/request → eligible donor groups.
- An ineligible group is never allocated.
- Exact-match-only fallback works if compatibility fallback is disabled.

### Sorting / searching
- Merge Sort returns correct ascending and descending order where supported.
- Quick Sort returns the same correct ordering as a trusted test expectation.
- Duplicate keys are handled deterministically.
- Binary Search returns the correct match / not-found result on a sorted array.
- Binary Search is never used on an unsorted array.
- Linear Search works on an unsorted array.

### Allocation workflow
- A request with enough compatible stock is fulfilled.
- A request with partial stock records allocated units and remaining shortage correctly.
- A request with no eligible stock remains pending and shows a shortage.
- Each bag can be dispatched at most once.
- A database failure does not produce a false success response.
- Cancelled/fulfilled requests cannot be processed again.
- Processing one request does not accidentally process all requests.
- A partially fulfilled request follows the documented requeue policy.

### API / UI
- Invalid blood groups, invalid urgency values, and non-positive quantities are rejected.
- Inventory and request forms show validation errors.
- Dashboard metrics change after adding stock, creating requests, and dispatching.
- Dispatch history reflects the actual allocation records.

## 13. Complexity Table to Include in the Project Report

Explain the complexity of the actual implementations used. A suitable starting table is:

| Operation | Data structure / algorithm | Expected complexity |
|---|---|---:|
| Peek next request | Binary heap | `O(1)` |
| Insert request | Binary heap | `O(log n)` |
| Remove highest-priority request | Binary heap | `O(log n)` |
| Peek earliest expiry in one group | Min-heap | `O(1)` |
| Insert/remove one bag in FEFO heap | Min-heap | `O(log n)` |
| Linear search | Array | `O(n)` |
| Binary search after sorting | Sorted array | `O(log n)` |
| Merge Sort | Array | `O(n log n)` time, `O(n)` extra space |
| Quick Sort | Array | Average `O(n log n)`, worst `O(n²)` |
| Hash-table lookup | Custom hash table | Average `O(1)`, worst `O(n)` |
| Database persistence | SQLite | Depends on query/index; do not claim a DSA complexity for all DB operations |

Do not claim the whole request allocation process is `O(log n)`: it may inspect several compatible blood groups and allocate multiple bags. Describe the overall cost based on the actual number of groups and bags processed.
